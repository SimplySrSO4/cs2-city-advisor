# 46 · 算法改进路线图（税收 × 幸福度 × 土地/交通效率）

> 本文件把 `45-economy-and-happiness.md` 的机制结论**翻译成可直接照着改代码的指标清单**。
> 对照对象：`references/70-carto-data-schema.md`（字段）、`scripts/city_report.py`（现有实现）、`scripts/core/carto_reader.py`（读取器）。
>
> 每条指标的字段说明：**指标名 → 计算公式 → 需要的数据字段 → 判读阈值 → 为什么对"税收/幸福度"有用 → 实现难度**。
> 难度定义：★ = 现有 reader 直接支持的十几行代码；★★ = 需要新增索引/几何运算；★★★ = 需要图算法或迭代求解。
>
> **数据可得性的硬边界（来自 `70-carto-data-schema.md` §5，本轮再次确认）**：
> Carto **没有**：地价、税率、预算、需求条、**建筑等级**、服务覆盖率、污染/噪音图层、拥堵、车速、通勤时间、公司利润、学历。
> → 凡是依赖这些字段的指标，**只能做代理**，并在报告里显式标注 `[代理]`。

## 1. 税收效率指标

### T1 · 税收潜力代理（Tax Potential Proxy）★★

**这是本轮最重要的新指标。** 依据（`45` §A1、§A3）：
- 住宅税基 = Σ 学历 `max(0, Wage(edu) − 1400)`；`Wage` 五档 ₡1500/1800/2100/2400/2700 → 应税部分 ₡100/400/700/1000/1300
- 商/工/办税基 = 公司利润 ∝ 效率 × 员工数（效率因子：员工幸福度、人手、专业化、水电费、邮件、签名建筑）
- 官方明文密度权衡：**低密度人均税多 / 高密度人多人均税少**

**公式（分三块，全部输出为"指数"，不输出 ₡）**：

```python
# 1) 住宅税收潜力（按建筑）
W = {"低密度": 1.0, "中密度": 0.72, "排屋": 0.85, "高密度": 0.55, "低租金": 0.35, "未知": 0.65}
# 权重来源：官方"低密度人均税多/高密度少"+"低租金明确更低"（定性 → 归一化为指数，非 ₡）
RES_TAX_PROXY(b) = Resident(b) * W[density_of(b.Name)]
# 2) 公司税收潜力（按建筑）
#    工业不论等级都倾向低学历 → 单位岗位的应税利润更低（工资成本低、产品价值低）
C = {"Industrial": 1.0, "Commercial": 1.35, "Office": 1.6, "Residential, Commercial": 1.2}
COM_TAX_PROXY(b) = Employee(b) * C[zone_of(b.Zoning)]
# 3) 全市
TAX_PROXY = Σ RES_TAX_PROXY * local_labor_share + Σ COM_TAX_PROXY * (1 - efficiency_penalty)
```

**需要的数据字段**：
- `Building_Boundary`: `Resident`, `Employee`, `Zoning`, `Name`, `Asset`
- `Area_Boundary`（行政区）: `Resident`, `Employee`
- **不需要新字段** —— 全部现有字段可算

**判读阈值**（**本项目自定义指数，非游戏数值**，必须在报告里如此标注）：
| 指标 | 判读 |
|---|---|
| `RES_TAX_PROXY / 住宅占地 m²` | 全市中位数以下 → 住宅用地"低产" |
| `COM_TAX_PROXY / 公司占地 m²` | 办公 < 商业 → 结构问题（见下） |
| `COM/RES` 比值 | < 0.6 → 城市过度依赖住宅税（人口一波动财政就崩） |

**为什么对税收有用**：Carto 拿不到税率与真实税收，但**能拿到"税基的三个要素"**（人数、岗位数、密度层级）。
这是目前唯一能把"用地结构"翻译成"税收结构"的可用代理。

**实现难度**：★★（需要一张 `Name`/`Asset` → 密度层级 的映射表；
`city_report.py` 已有 `analyze_zoning()` 里的密度识别代码，直接复用即可）

> ⚠️ **必须写在报告里的话**：本指标是**相对指数**，权重由官方定性结论归一化而来，**不代表 ₡ 金额**。

### T3 · 本地劳动力自给率 / 城外通勤缺口 ★

**依据**（`45` §A5）：官方明文——城外通勤者**完全不向本城缴税**；住城内/城外上班的居民也**不缴税**。

**公式**：
```python
LOCAL_LABOR = Σ Building.Resident * LABOR_PARTICIPATION   # 建议 0.55～0.65，标注为[经验值]
JOBS        = Σ Building.Employee
SELF_SUFFICIENCY = min(1.0, LOCAL_LABOR / JOBS)      # = 岗位由本地人填补的比例
COMMUTER_GAP     = max(0, JOBS - LOCAL_LABOR)        # 对住宅税零贡献的岗位数
```
**分区级**：对每个 `District` 同样计算，找"岗位/人口"极端区。

**需要的数据字段**：`Building.Resident`、`Building.Employee`、`Area_Boundary`（District）

**判读阈值**：
| 指标 | 判读 |
|---|---|
| `SELF_SUFFICIENCY < 0.85` | 岗位大量靠城外通勤者填 → **公司效率有了，但住宅税收拿不到**。要么补住宅，要么承认这块岗位只产生"公司税" |
| `COMMUTER_GAP / JOBS > 0.3` | 严重依赖城外劳动力 → 一旦外部连接拥堵/断开，公司效率会崩 |
| 区级 `岗位/人口 > 1.5` | 就业飞地：本地无人可税，通勤全部跨区 → 1.6.0f1 后是**辞职风险区** |

**为什么对税收有用**：**这是"岗位多 ≠ 税收多"的直接量化。**
上一轮 `SKILL.md` 只说"注意城外通勤者不纳税"，没有给出**可计算的缺口**。

**实现难度**：★（现有 `analyze_city()` 已算 `job_housing_ratio`，加两行即可）

### T7 · 低密度地价风险敞口（税率敏感区识别）★

**依据**（`45` §C1.4、§A2.1）：官方明文——**低密度住宅的地价上升全部由单一住户承担**；
且 `Rent = (LandValue + ZoneType×Level) × LotSize × SpaceMultiplier` → 低密度 `LotSize` 大，租金对地价更敏感。

**公式**：
```python
LOW_DENSITY_EXPOSURE(district) =
      (低密度住宅 Resident 数) / (该区住宅 Resident 总数)
    * (该区住宅建筑数 / 该区住宅占地 m²)      # 稀疏度：越低越脆弱
    * NORM(该区住宅建筑平均占地 m²)            # LotSize 代理
```
**需要的数据字段**：`Building.Name`/`Asset`（密度层级）、`Building.Resident`、建筑 polygon 面积

**判读阈值**：
| 指标 | 判读 |
|---|---|
| 区级 `LOW_DENSITY_EXPOSURE` 位于全市 Top 25% | **该区是"涨税/涨地价"的第一批受害者** → 调税率前先看这里 |
| 区级低密度占比 > 60% 且 平均占地 > 300 m² | 高脆弱；**建议该区住宅税率低于全市均值** |

**为什么对税收有用**：官方**没有**给税率甜蜜点（C16），但机制上"高税率 → 低密度先崩"。
→ **可行的替代策略不是"找全局最优税率"，而是"按区差异化税率 + 先识别脆弱区"。**
这条指标就是给差异化税率提供落点。

**实现难度**：★

### T13 · 学历—岗位错配代理 ★★

**依据**（`45` §A1.2）：住宅税基 **13 倍差距**取决于学历（Uneducated 应税 ₡100 vs Highly Educated ₡1300）；
官方另明文：**工业不论等级都倾向低学历岗位，商业/办公随等级上移偏高学历**。

**公式**：
```python
# 用资产名/分区做"岗位学历结构"的粗代理
EDU_MIX(b) = {
  "Industrial":  {0:0.45, 1:0.30, 2:0.15, 3:0.07, 4:0.03},   # 工业偏低学历（官方定性）
  "Commercial":  {"L1":{...低}, "L3":{...中}, "L5":{...高}},   # 需按 Name/Asset 判等级
  "Office":      {"L1":{...中}, "L5":{...高}},
}
TAXABLE_WAGE_POOL = Σ_b Employee(b) * Σ_e EDU_MIX(b)[e] * max(0, WAGE[e] - 1400)
```
**需要的数据字段**：`Building.Employee`、`Building.Zoning`、`Building.Name`/`Asset`（判等级）

**判读阈值**：
| 指标 | 判读 |
|---|---|
| `TAXABLE_WAGE_POOL / JOBS` 低（示例 < ₡600） | 岗位结构偏低学历 → **交了教育费但拿不到应税工资** |
| 工业岗位占比 > 55% 且 办公岗位占比 < 10% | 结构性低税基 |

**为什么对税收有用**：把"学历结构"（住宅税收的唯一真正杠杆）**从不可测量变成可代理**。

**实现难度**：★★（需要一张 `Asset → 等级` 映射表；**1.5.2f1 后资产可自制** → 该表需要可配置，
不能硬编码。建议做成 `assets_density_levels.json` 外部配置文件）

## 2. 土地利用效率指标

### T2 · 逐栋容积率代理（FAR Proxy）★

**本轮第二个关键指标。** Carto **有建筑 polygon**（`Building_Boundary` 是 `PolygonZ`），
`carto_reader` 已有 `polygon_area()` —— 但 `city_report.py` **目前只对 District 和 Zoning 用了它，没对建筑用**。

**公式**：
```python
FOOTPRINT(b)      = polygon_area(b)                      # 建筑占地 m²
FAR_POP(b)        = Resident(b) / FOOTPRINT(b)  * 10000  # 人 / 万 m²
FAR_JOB(b)        = Employee(b) / FOOTPRINT(b)  * 10000  # 岗 / 万 m²
# 分区/网格聚合
FAR_ZONE(z)       = ΣResident / ΣFOOTPRINT   （按 Zoning 分组）
```
**需要的数据字段**：`Building_Boundary` 的几何（**已有**）+ `Resident`/`Employee`/`Zoning`

**判读阈值**：
| 指标 | 判读 |
|---|---|
| 同类分区（同密度层级）内 `FAR_POP` 的 P10/P90 差距 > 3× | 存在**明显低效的建筑群** → 该处是加建/重划的目标 |
| `FAR_JOB`（办公）< 全市办公中位数 50% | 办公用地浪费（可能被低等级建筑占着） |
| `FAR_JOB`（工业）异常高 | 1.1.5f1 起工业 space multiplier = 5 → 正常会很高，**不要误判为异常** |

**为什么对税收有用**：这是**唯一能拿到的"土地强度"字段**。
`税收潜力 / 占地` = `TaxProxy / Footprint` 就是本轮核心目标（单位土地税收）的**可算版本**。

**实现难度**：★（`polygon_area()` 已存在，加一个分组求和）

### T4 · 已划区未建地块（土地浪费）★★

**依据**：`Zoning_Boundary` 是 **8 m × 8 m ≈ 64 m² 的固定栅格单元**（`70` §3.2 实测）；
`Building_Boundary` 是真实建筑轮廓。**两者相减 = 已划区但没有建筑覆盖的单元**。

**公式**：
```python
# 1) 把每个 Zoning 图斑的质心当作一个 8m 单元
# 2) 对每个单元，检查是否落在任一 Building polygon 内（用 GridIndex 加速）
ZONED_CELLS      = 所有 Zoning 图斑
BUILT_CELLS      = { c ∈ ZONED_CELLS : ∃ building b, centroid(c) ∈ polygon(b) }
VACANT_RATIO(z)  = |ZONED_CELLS(z) − BUILT_CELLS(z)| / |ZONED_CELLS(z)|
```
**需要的数据字段**：`Zoning_Boundary` 几何与 `Zoning`；`Building_Boundary` 几何

**判读阈值**：
| 指标 | 判读 |
|---|---|
| 全市 `VACANT_RATIO > 0.35` | 划了太多区没建起来 → 需求不足 or 服务/道路不通 |
| 某分区 `VACANT_RATIO > 0.5` 且需求条该类型为高 | **矛盾信号**：划了区却没人来 → 查地价/污染/可达性 |
| 某分区 `VACANT_RATIO > 0.5` 且需求条为低 | 正常，是预留地 |
| 成片（> 20 个连续单元）空缺 | **土地闲置热点** → 报告里给出坐标簇 |

**为什么对税收有用**：闲置的已划区 = **零税收土地**。
这是"用地效率"最直接的浪费指标，且**完全不需要游戏内读数**。

**实现难度**：★★（点-多边形包含判定 + 空间索引；`carto_reader.GridIndex` 已有 `within()`，
但那是圆形半径检索 → 需要新增 `point_in_polygon` 或退化为"建筑 bbox 覆盖"的近似。建议先做 bbox 近似版）

### T9 · 混合用途口径修正 ★

**问题**（`45` §C4.1）：`Zoning == 'Residential, Commercial'`（Mixed Housing，里程碑 5）**同时产生住宅与商业**。
`city_report.py` 的 `analyze_zoning()` 把它当独立一类统计，**没有并入住宅口径**。

**修正**：
```python
RES_ZONES = {"Residential", "Residential, Commercial"}
COM_ZONES = {"Commercial", "Residential, Commercial"}
# 分区结构表新增一列"口径"，并同时给出两种口径：
#   严格口径（Residential 单列） / 合并口径（含混合用途）
```
**判读**：混合用途占比 > 15% 时，**必须用合并口径**，否则住宅人口被系统性低估。

**实现难度**：★

**公式**：

## 3. 幸福度风险指标

### T5 · 住宅噪音暴露指数（含"隧道 = 0"官方规则）★★

**依据**（`45` §C4.3、§D2.2）：官方**明确**——隧道噪音被完全抑制、高架噪音被放大、树木只有很弱降噪；
官方道路表给出**每条道路的 Noise pollution factor**（1× / 2×）。

**公式**：
```python
ROAD_NOISE_W(seg) = NOISE_FACTOR[seg.Asset]      # 官方表：1 或 2
                  * (seg.Lane or 1) / 2.0          # 车道数加权
                  * (1 + (seg.Limit or 40) / 100)  # 限速加权
                  * FORM_MULT[seg.Form]            # Normal 1.0 / Elevated 1.4 / Tunnel 0.0  ← 官方规则
RES_NOISE(b) = Σ_{seg : dist(seg, centroid(b)) < R} ROAD_NOISE_W(seg) / max(dist_m, 30)**2
NOISE_RISK(district) = Σ_{住宅建筑 b} Resident(b) * RES_NOISE(b)
```
**需要的数据字段**：`Network_Centerline` 的 `Asset` / `Lane` / `Limit` / `Form` / `Category`；
`Building_Boundary` 的 `Resident` + 质心；**道路资产名 → 官方 noise factor 映射表**（从 `40-number-tables` / Wiki Roads 表生成）

**判读阈值**：
| 指标 | 判读 |
|---|---|
| 某住宅建筑 `RES_NOISE` 位于全市 P90 以上 | **该建筑是"高税+高噪"双杀点** → 优先迁走噪音源或加隔音墙 |
| 住宅沿 `Category=Highway` 500 m 内 | 官方明确高速噪音在 1.1.6f1 被上调 → 直接标红 |
| 干道上无 `Speed Bumps` 政策覆盖的住宅段 | Speed Bumps 官方"大幅降噪音" → 低成本改善项 |

**为什么对幸福度有用**：噪音是官方 10 个幸福度因子中**唯一有官方量化权重**（noise factor 1×/2×）的一个，
而且 `Form == 'Tunnel' → 权重 0` 是**官方明文规则**，可作为精确的算法分支。

**实现难度**：★★（需要"道路资产名 → 官方 noise factor"映射表；
可从 `https://cs2.paradoxwikis.com/Roads` 的自动生成表批量抽取）

### T5b · 服务覆盖缺口代理 ★★

**依据**（`45` §B5）：`Service range` 单位未公开 → **不能用它的数值**。
改用 **POI 坐标 + 自己圈定的现实标准半径**。

**公式**：
```python
# POI_Location 的 Category 分类：医疗/教育/警察/消防/邮政/电信/公园/交通枢纽
COVERED(pop_or_jobs, R) = Σ_{建筑 b : ∃ poi, dist(b, poi) < R} (Resident or Employee)
GAP_SERVICE(R) = 1 - COVERED(Resident, R) / Total_Resident
```
**半径取值**：400 / 600 / 800 / 1200 / 2000 m **多档并列输出**，并**显式标注"现实标准半径，非游戏 Service range"**。

### T5c · 通勤可达性代理（路网最短路）★★★

**依据**（`45` §D1.2）：1.6.0f1 起寻路距离上限**按出行目的分设**，找不到路就**辞职/搬离**。
→ "有没有一条可行路线"比"路线多快"更关键。

**公式**：
```python
# 1) 用 Network_Centerline（Object == 'Road'）建图，节点 = 端点吸附（容差 ~25 m）
# 2) 就业中心（T16 的 Top-N 网格）为起点集，住宅聚类为终点集
d = dijkstra(就业中心, 住宅聚类)          # 路网距离，不是欧氏距离
COMMUTE_RISK = Σ_{住宅聚类} Resident * I[d > D_LIMIT]
```
**D_LIMIT 取多少**：**官方没有公布四类出行的上限数值**（C 系待验证）。

**判读**：

| `d > 12 km` 的住宅人口占比 > 10% | **1.6.0f1 后属高危**：可能已出现"辞职/搬离" |
| `d > 8 km` 的住宅人口占比 | 用同城历史导出对比趋势（`70` §5 局限 1：Carto 只有快照 → 必须多次导出） |

>   只负责给线路提供车辆）；`StopCargoTrain` / `StopCargoShip` 属货运，归工业部分。
> * **T14 货运终端集疏运是唯一的货运指标**，它**只服务工业部分的辅助分析**，

### T17 · 候车时间的两项分解：`E(W) = E(H)/2 × (1 + C²)` ★★★（`references/61` 新增，价值最高）

**来源**：`references/61-transit-planning-and-operations.md` §2.6（Ceder《公共交通规划与运营》式 12.1，印刷 p277 附近）。

**为什么这条最重要**：它把"候车时间"拆成**两个可独立下手的东西**：

| 符号 | 含义 | 游戏里对应 |
|---|---|---|
| `E(H)` | 平均发车间隔 | **加车**（`车辆数`）—— 要花钱、受 depot 上限约束 |
| `C²` | 发车间隔的**变异系数平方**（规律性） | **运行是否规律** —— 受拥堵、专用道、调度影响 |

**两种极端**：班次完全规律时 `C² = 0` → `E(W) = H/2`；完全乱序时 `C² = 1` → `E(W) = H`。
**⇒ 在车辆数不变的前提下，把 `C²` 从 1 压到 0，候车时间直接砍半。**

**这对 CSL2 建议的直接影响（重要）**：
- 现实里给公交的收益排序是 **"服务质量弹性 (0.5–0.7) > 票价弹性 (−0.2 ~ −0.5)"**
  → **"降价换客流"效率低，钱应该花在缩短/稳定候车上**（见 `61` 表 11.3）。
- 走行/候车时间的权重（Balcombe 2004）：**步行 ×1.68、步行+换乘 ×1.81、等待 ×1.76、发车间隔 ×0.77**
  （以车内时间为 1）→ **缩候车与缩步行，比提车速更值钱**。
- **公交专用道/信号优先在现实中的真实收益是"降方差、减串车"，不是提车速**
  （`61` 表 17.4：苏黎世信号优先 + AVL 只让车速 +1.9 km/h；都柏林"均值没降、方差降了"；
  雅典专用道让部分线路乘客 +10%）。→ **在 CSL2 里给专用道的理由应当是"让车不串、间隔稳定"**，
  而不是"让车更快"。

**在 Carto 数据上能做到什么**（诚实边界）：
`C²` 需要**逐车次到站时间序列**，Carto **没有**。所以：
- **可以直接算**：`E(H)`（现有 `approx_headway_min_at_20kmh`）、每线路 `人/车`（**与容量归一的线路效率一并给，见 T6**）、走廊级间隔（T6）；
- **不能直接算**：`C²`。→ **改为"可观测的代理"**：同一线路**乘客数在多次导出间的波动**、
  线路是否经过**拥堵干道**（用 §3 的限速/车道/等级推断）、是否**有专用道**
  （Carto 的 `Category` 带 `, Bus` 后缀 → **可判**！见 `70-carto-data-schema.md`）。
- **给玩家的一句话**：`如果一条线有专用道（Category 含 Bus）却仍然客流差，问题多半在 E(H)（车不够），
  不在规律性；如果没专用道且穿拥堵路段，先上专用道压 C²，再加车。`

**实现难度**：低（判 `Category` 是否含 `Bus` + 与拥堵代理交叉）—— 建议**下一轮加进 `city_report.py`**。

### T6 · 走廊运力—需求匹配 ★★
**现有实现**：`analyze_overlap()` 已有"400 m 内占比 ≥ 80% → 同一走廊"的判读。
**缺口**：只有几何重叠，**没有运力与需求的对比**。

**新增公式**：
```python
# 把同一走廊的线路聚成一簇，比较簇内"总运力"与"总客流"
CORRIDOR = cluster(routes, dist_400m_share >= 0.8)
routes   = [r for r in routes if r.Vehicle > 0]     # 先剔除停用线路（Vehicle == 0，见下）
CAPACITY_PROXY(c)   = Σ_{r ∈ c} Vehicle(r)                     # 车辆数，官方字段
DEMAND_PROXY(c)     = Σ_{r ∈ c} Passenger(r)                   # 在线乘客数，官方字段
LOAD_PER_VEHICLE(c) = DEMAND_PROXY / CAPACITY_PROXY            # = 人/车（原值，必须保留）
CAPACITY_SEATS(c)   = Σ_{r ∈ c} Vehicle(r) * 单车容量(r)        # 单车容量见 40 表
LOAD_FACTOR(c)      = DEMAND_PROXY / CAPACITY_SEATS            # = 容量归一的线路效率（"满载多少趟"）
HEADWAY(c)          = 2 * (Length(c)/2 / v) * 60 / CAPACITY_PROXY(c)   # v 取 20–25 km/h
# 线路总里程（线网规模 / 密度 / 按方式汇总）一律 = Σ Length(r)，逐线路长度相加
```

> **三条口径（必须一起用，详见 `70-carto-data-schema.md` 3.4 与 `30-public-transport.md` A3.7–A3.8）**：
> * **容量归一**：`线路效率 = 乘客数 ÷（车辆数 × 单车容量）` —— 单车容量见 `40-number-tables.md` 1.3 表
>   （公交 **80** / 地铁 **1080** / 客运火车 **840** 人/辆；**电车 / 单轨 / 渡轮 / 缆车容量未知 → 不做归一、留空**）。
>   **必须同时保留「人/车」原值** —— **只按「人/车」横向排序会把"地铁车大"误读成"地铁低效"**。
> * **停用线路排除**：`Vehicle == 0` 的线路**先剔除**，**不做任何客流分析**（人/车、人·km、估算间隔、
>   效率排序、客流合计与中位数），**只做线位分析**（走向 / 长度 / 站数 / 覆盖贡献 / 是否与既有走廊重复），
>   并在报告里**单独列停用线路清单**（处方：① 恢复配车 ② 撤线）—— **不得混进"低效线路"批评**。
> * **里程口径**：**线路总里程 = 逐线路 `Length` 相加**，单线明细表 / 按方式汇总 / 线网规模 / 线网密度
>   **同一个口径**；线网合计与逐线明细对不上时**以逐线相加为准**，**不再保留另一套合计去核销差额**。

**判读阈值**：
| 指标 | 判读 |
|---|---|
| 走廊内 2 条线，**`LOAD_FACTOR`（容量归一）**均低于同城中位数 | **合并**：车辆数相加 → 间隔减半 → 官方明文"缩短候车时间会影响寻路计算" |
| 走廊 `HEADWAY > 8 min` 且 **`LOAD_FACTOR`** > 中位数 | **加车**（间隔是瓶颈，不是需求） |
| 走廊 `HEADWAY < 4 min` 且 **`LOAD_FACTOR`** < 中位数 50% | **减车/并线**（过度供给） |

> ⚠️ 跨方式比较**只用 `LOAD_FACTOR`（容量归一）**；`LOAD_PER_VEHICLE`（人/车）**只在同一方式内部比较**
> （地铁一辆车 1080 人 vs 公交一辆车 80 人，混排会得出相反结论）。

**为什么对交通/税收有用**：修车是**纯成本**（depot + 车站维护费），不会带来税收；
它只能通过"可达性 → 地价/幸福度"间接回本。**所以加车必须加在有需求的地方。**

**实现难度**：★★（`analyze_overlap()` 已有 80% 判据，把 pairs 升级成 clusters 即可）

### T10 · 路网"车道·公里"口径修正 ★

**问题**（`70` §4 已指出）：双向高速在数据里**按方向各记一条**（`Direction=Forward`），
`city_report.py` 的"高速里程占比"因此**把双向路幅算了两次**（报告里只是打了个警告）。

**修正公式**：
```python
lane_km(seg) = (seg.Lane or 0) * seg.line_length() / 1000
# 口径说明：
#   Direction == 'Forward' → 该记录本身就是单向路幅，Lane 是单向车道数 → lane-km 正确
#   Direction == 'Both'    → 该记录含双向，Lane 是双向总车道数 → lane-km 正确
#   里程口径（现有）才是会重复的那个 → 用 lane-km 作为主口径，里程作为副口径
ROAD_MIX = { cat: Σ lane_km }   # 替代现有的 { cat: Σ length }
```

| 指标 | 判读 |

| `highway_lane_km / total_lane_km > 0.35` | 高速路幅占比过高（**新阈值，因为 lane-km 口径下比例天然更高**） |
| `Small lane_km / Medium lane_km < 1.5` | 支路网不足 |
| **同等级道路的 `lane_km / km` 均值** | 用于识别"同等级但路幅异常"的段落 |

### T18 · 真实站点覆盖率（**客运**口径；`city_report.py` §15 已实现）★★

|---|---|---|---|
| **0** | ⭐ **四项基础的状态**：① 人口分布是否明显失衡 ② **失业率百分比** ③ 公交跟不跟得上规模 ④ 路网分级是否合理 | 报告 §0.5；失业率在游戏内 **Unemployment** 面板 | **第 1 层的准入条件**（`SKILL.md` 核心目标）。**基础未达标时，下面这些税收读数先别问** —— 先修基础 |
| **1** | **四类税率的当前值**（住宅 5 档学历分别的值；商/工/办按产品类型的值） | Economy → Taxation | **T1 的权重标定**与 T7 的差异化税率建议都需要它 |
| **2** | **Building Level 视图里各分区各等级的占比**（L1–L5 各多少栋/多少%） | Info Views → Building Level | **升级 = 税收的长期决定因素**（`45` §C2）。没有这个数就无法判断"税基会不会自己涨" |
| **3** | **财政面板**：税收总额 + 四类分区拆分、服务费收入、进口服务支出、月结余 | Economy → Budget | **把 T1 的相对指数锚定成 ₡**（唯一办法） |
| **4** | **各服务预算滑块的位置**（电力/水/垃圾/教育/医疗/交通/公园…） | Economy → Budget | `45` §A4.1：预算**同时影响容量与工资支出** |
| **5** | **需求条 RCIO 四个数** | 主界面需求条 / 截图 | 与 T4（已划未建）交叉验证：划了区但需求为高 = 有阻塞 |
| **6** | **全城幸福度 + Happiness 视图里的因子明细** | Info Views → Happiness | 官方 10 因子的**实测权重不明** → 只能靠玩家读数定位短板 |
| **7** | **平均地价**（Land Value 视图光标读数；重点看几个小区的值） | Info Views → Land Value（1.1.0f1 起光标显示金额） | `Rent = (LandValue + ZoneType×Level) × LotSize × SpaceMultiplier` 的**唯一输入源** |
| **8** | **各线路面板的"使用率百分比"** | Transportation Overview → Line Details | `Route.Usage` **不能当百分比**（`70` §3.4）→ 加车判断只能用游戏内的数 |
| **9** | **Workplace Availability 按学历的岗位数**（5 档） | Info Views → Workplace Availability | **T13 的唯一校准源**；也是"学历过剩"诊断的核心 |
| **10** | **公司盈利视图**：各分区平均利润 / 亏损公司占比 | Info Views → Company Profitability | **商/工/办税收 = 利润 × 税率** → 这是税基的直接读数 |
| **11** | 服务不足提示清单（垃圾/医疗/殡葬/消防/警力/邮政/通信 各自有没有报警） | Chirper / 各服务面板 | 补 T5b 覆盖分析看不见的**容量型**缺口（覆盖到了但排队） |

> 📌 其中 **RCIO 需求条 + 失业率**在 DSH 插件里由工具 **`csl2_city_readings`** 采集
> （可视化滑动输入、用户可跳过）；标准数据结构与档位口径见 `120-rcio-input-step.md`，
> 流程见 `SKILL.md` §1 第 0 步（**「数据前置」条**）。

> ⚠️ **第 0 项是门槛，不是可选项。** `失业率` 在 Carto 里**没有对应字段**（已核实全部图层字段），
> 报告 §0.5 只能给「岗位 ÷ 劳动力」的**供需代理** —— 它**测不出结构性失业**（学历与岗位不匹配），
> 所以**必须让玩家读游戏内的 Unemployment 百分比**。

**建议的提问模板**（一次问 6 项，避免信息过载）：
```
1) 版本号（主菜单右下角）
2) 人口 / 岗位 / 失业率 / 幸福度        ← 失业率属于第 1 层，优先问
3) 四类税率当前值（住宅如分了学历档请一并给出）
4) Building Level 视图：住宅/商业/工业/办公各等级占比
5) 财政面板：总收入、四类税收拆分、月结余

```

## 7. 不可逾越的红线（写代码时别忘了）

1. **不输出 ₡ 金额**，除非玩家给了财政面板读数用于锚定。
2. **不说"Service range 是米"**（C10 / C20）。
3. **不设"幸福度 < X 报警"的绝对阈值**（`45` §B4：官方无阈值）。
4. **不引用"税率甜蜜点"的具体数字**（C16）。
5. **`Route.Usage` 不当百分比**（`70` §3.4）。
6. **Zoning 图斑面积不当用地面积**（`70` §3.2）——但 **Building polygon 面积可以当占地面积用**。
7. **代理指标的权重必须标 `[经验值]` / `[推导]`**，且集中放在一个可配置的常量区，方便版本更新后重标定。
