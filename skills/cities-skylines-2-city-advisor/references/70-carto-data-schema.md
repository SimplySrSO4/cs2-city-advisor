# Carto 数据导出格式与字段速查（CSL2）

本文件说明 Carto Mod（Cities: Skylines II）导出的城市数据长什么样、每个字段是什么意思、怎么读。
`scripts/core/carto_reader.py` 与 `scripts/city_report.py` 就是按这份规格写的。

## 1. 目录结构

### 1.0 游戏自己写出的位置（**不必手动复制**）

Carto 默认把数据写到 Unity 的 persistentDataPath：

```
%USERPROFILE%\AppData\LocalLow\Colossal Order\Cities Skylines II\ModsData\Carto\
├─ Shapefile\   35 个文件（.shp/.shx/.dbf/.prj/.cpg）
├─ GeoTIFF\     4 个（Elevation / Depth / WorldElevation / WorldDepth）
└─ Styles\      QGIS 样式（Plan / Street / Topo 三个子目录，只有 .qml）
```

**脚本可以直接读这个目录**，不必先复制到工作区：

```python
from carto_reader import find_game_carto_dir
find_game_carto_dir()      # → 上面那个路径（自动挑最近修改的候选）
```
或显式传路径：`city_report.py --carto "%LOCALAPPDATA%..\LocalLow\Colossal Order\Cities Skylines II\ModsData\Carto"`。

> ⚠️ 实测：**游戏内原始导出的记录数与工作区副本完全一致**（Area 235 / Building 1754 /
> Network 1567 / POI 559 / Route 11 / Zoning 26691）→ **复制这一步不会丢数据**，
> 但也没必要做。`Styles\` 下的子目录**只有 QGIS 样式，没有数据**。

### 1.0.1 存档（Saves）能提供什么

```
...\Cities Skylines II\Saves\<SteamID>\*.cok        ← 存档本体（**ZIP 容器**）
```

* `.cok` 是 **ZIP**，内含 8 个条目；其中 **`*.SaveGameMetadata` 是纯 JSON**，
  可以**直接读出：城市名 / 人口 / 资金 / 游戏内日期 / 主题 / 地图名 / 启用的 Mod 列表**。
  工具：`carto_reader.list_saves()`、`read_save_metadata()`。
* **`*.SaveGameData`（约 71 MB，未压缩）是二进制 ECS 序列化数据**。实测其中
  **只有系统/组件名是可读 ASCII**（如 `TrackCompanyCustomersAndTaxes`、`LevelUpStatistics`），
  **没有可搜索的"值"** —— 搜 `Tax`/`Residential`/`Rent`/`LandValue`/`Profit` 都几乎为零命中。
  **⇒ 想从存档里取出税率、建筑等级、公司利润、地价，需要反序列化整套类型体系，成本很高，
  目前不具备可行性。** 这些值仍应让玩家在游戏内视图读数（见 `46` §5.2）。

> ⚠️⚠️ **存档元数据的人口数字与 Carto 汇总的口径不同，不要混用。**
> 实测同一座城：存档元数据 `population = 81163`（游戏 UI 口径），
> 而 Carto 逐栋 `Resident` 求和 = **70,587**（已落地居民口径）。
> 两者差约 13%，且**存档时间（19:13/19:14）晚于 Carto 导出时间（16:31），中间城市还在长**。
> **⇒ 引用人口时必须写明来源与时间点**；要做趋势对比，两次导出之间不要跨存档。

### 1.0.1b ⭐⭐ 游戏内时间：**能读到**，且跨期比较**必须先比它**

**这是最容易得出错误结论的地方**：`Passenger`（线路乘客数）、`Volume`（车流量）、
拥堵程度等读数**随一天内的时段剧烈变化**。两次存档分别落在**早高峰**与**凌晨**时，
客流差异**几乎全部由时点造成** —— 读成"公共交通客流下降"是**错的**。

#### 怎么读（已验证）—— **自动读取，不需要用户输入**

`<城市名>.SaveGameMetadata`（`.cok` ZIP 内的纯 JSON）含：

```json
"simulationDate": { "year": 2031, "month": 1, "hour": 23, "minute": 22 }
```

工具（`core/carto_reader.py`）：
* `list_saves(save_dir=None)` —— 列出全部存档及其元数据（按文件时间倒序）
* `read_save_metadata(cok_path)` —— 城市名 / 人口 / 资金 / **年·月·日·时·分** / 主题 / 地图 / Mod
* `save_game_clock(meta)` —— 格式化成 `"2031-01-22 23:22"`
* `carto_export_time(carto_dir)` —— 导出的**数据**时间（见下方 ⚠️）
* **`attach_game_time(carto)`** —— ⭐ **默认入口**：自动匹配存档并返回时间 + 置信度
* `find_save_for_carto(carto)` —— 底层匹配函数，返回 `(meta, why)`；`meta["_match"]` 带诊断信息

**实测样例**：同一台机器上 `静海 2` = 2030-09 **01:34**（凌晨）、
`静海` = 2034-05 **13:13**（下午）、`江东` = 2031-01 **23:22**（夜间）。

#### ⚠️ 为什么"自动匹配"只能推断（三层局限，都已实测）

1. **Carto 导出是按需触发的，与"保存游戏"不耦合。**
   实测某次导出在 `2026-10-14 00:23`，而前后最近的存档是 `10-10 22:28`（3.1 天前）
   与 `10-14 13:07`（12.7 小时后）—— **导出时刻根本没有对应存档**。
2. **GeoJSON 文件名不含城市名**（`Area_Boundary.json` 等；新版前缀命名不是必然）。
3. **Carto 建筑人口合计 ≠ 存档 `population`**（口径不同：存档含无家可归者等，
   且导出与存档的时刻不同、城市还在长）。实测同一座城比值约 **0.84**；
   而**别的城市**比值可到 0.42 / 1.60 / 2.64 / 4.30 —— 这正是区分"同城/异城"的依据。

**⇒ 匹配规则**（`find_save_for_carto()`，返回结果**必带置信度**）：

| 步骤 | 规则 |
|---|---|
| ① 人口合理性过滤 | `Carto 人口 ÷ 存档 population ∈ [0.5, 2.0]` → 排除同机器上的**其它城市** |
| ② 取时间最接近 | 在候选里选 `\|存档 mtime − 导出数据时间\|` 最小者（**不分前后** —— 可能先导出后保存，也可能反过来） |
| ③ 窗口限制 | 时间差 > **72 h** 视为无效 |
| 置信度 | ≤2 h → **高**；≤24 h → **中**；否则 **低**（报告会提示"建议导出后立刻存档"） |

> ⚠️ **不要用 Carto 目录的 mtime 当导出时间。** `ModsData\Carto\` 的目录 mtime 会被
> **任何子项写入**顶掉 —— 实测 `Styles/*.qml` 在另一时刻生成，把导出时间从 `00:23`
> 误判到 `10:29`（差 10 小时）。**必须用 `carto_export_time()` 取数据文件的最新 mtime。**

**⇒ 最佳实践（要写进给玩家的建议里）：`导出 Carto 之后立刻保存一次游戏`**，
这样匹配几乎必然正确（时间差接近 0）。

#### 可比性判据（`compare_game_time()`）

时段：`凌晨 0–5` / `早高峰 6–9` / `日间平峰 10–15` / `晚高峰 16–19` / `夜间 20–23`。

> ⚠️ **商业利润对时点敏感（本表唯一的经济类例外）**：商业盈亏随**营业时段**变化 ——
> **凌晨（0–5 时）存档大概率亏损，日间则不一定**。所以**「公司利润 / 亏损公司占比」跨时段比较时，
> 必须同时报告存档时点**；**凌晨存档里的商业亏损不作为证据**，结论要降级为
> 「需白天（10–19 时）复导一次再判」。商业热门时段 = **日间平峰 10–15 时 + 晚高峰 16–19 时**
> （**`[经验]`，无官方来源**）。工业 / 办公 / 住宅的公司利润敏感度低得多，不受此限。

| 情形 | 判定 | 客流/流量类 |
|---|---|---|
| 同一时段 | **可比** | ✅ 能比 |
| **凌晨 ↔ 通勤峰** | **不可比**（硬规则） | ⛔ 深夜与峰是**数量级**差异 |
| 环形小时差 **≤3 h** | **需谨慎** | ⚠️ 只作方向性参考 |
| 环形小时差 **>3 h** | **不可比** | ⛔ 不能比 |

> ⚠️ **必须用「环形小时差」，不能用「时段序号差」。** 时段序号会把
> 「凌晨(序号0) → 早高峰(序号1)」误判成"相邻"，而那恰是最该拦住的组合（实测已踩）。

**指标按"时点敏感度"分三类**（`METRIC_TIME_SENSITIVITY`）：

* **强敏感**（跨时段**禁止**数值比较）：`Passenger`、站点/线路客流、断面客流、
  `Volume` 与单车流量、拥堵程度、商业顾客数、公交候车与在车人数、步行与自行车流量；
* **中等**：就业中心分布、通勤距离分布、服务设施负载、垃圾/殡葬等服务压力；
* **弱敏感**（**任何时间都能比**）：人口/岗位/职住比、建筑数与建筑等级、分区图斑、
  路网与轨道里程、**配车数 `Vehicle`**、线位几何、站数、**工业 / 办公 / 住宅的公司利润**、
  地块解锁数、地形量、税基结构。
* ⚠️ **例外：商业利润是时点敏感的** —— 商业盈亏随**营业时段**变化（**凌晨 0–5 时大概率亏损、
  日间不一定**），所以「**公司利润 / 亏损公司占比**」**对商业不能当弱敏感指标用**：
  **跨时段比较商业利润必须同时报告存档时点**，**凌晨存档读出的商业亏损不作为证据**
  （判据与热门时段定义见 `45-economy-and-happiness.md` A1.4–A1.5）。

#### 建议下次存档时间（`recommend_save`）

按**上一期的时段**给具体窗口：上一期 08:12（早高峰）→ 建议 **07:00–09:00**；
上一期 03:40（凌晨）→ 建议 **00:30–05:30**；两次已在同一时段 → 保持即可。
输出同时说明："**若只关心不随时段变的指标（人口/岗位/建筑等级/配车数），任何时间存档都可以。**"

#### 报告里的落地位置

**§20.0 ⏰ 先判时点可比性** —— 排在 `--prev` 所有数值增量**之前**，含
「上一期/本期时间 + 时段 + 时间来源 + 结论 + 可比清单 + 不可比清单 + 下次存档建议」。
判为 `不可比`／`未知` 时，**线路表自动隐去「乘客变化」列**（只留配车数与线路增删）。

> ⚠️ **`--prev` 的两个 `CartoData` 都必须 `apply_unlocked_clip()`**：
> 只裁剪本期会让"裁剪后 vs 未裁剪"的**纯口径差**被当成里程增减
> （实测同一目录自比显示 **−91 km**）。此 bug 已修。


### 1.0.2 ⭐ 新版 GeoJSON 比旧版 Shapefile **多了这些字段**（**已并入计算**）

> ✅ **这些字段已实装**：`analyze_real_tax_base()`（报告 **§8.2**）用的是真实 `Profit` / `Wage` / `Level`，
> 不再依赖 `DENSITY_TAX_WEIGHT` / `ZONE_JOB_WEIGHT` 那套代理。**§8.2 可用时以它为准，§11 降为备选口径。**

### 1.0.2b ⭐⭐ `Wage` 口径变更 ——**必须区分新旧**

| | 旧导出（≤18:44） | **新导出（22:01 起）** |
|---|---|---|
| `Wage` 含义 | 平均**总**收入 | **劳工平均应税收入**（起征点已在字段内） |
| 实测中位 | 2385 | **1408** |
| 实测 max | 8157 | 6501 |
| 高频取值 | 2300 / 2400 / 2200 / 2500（整百、簇状） | 1300 / 1400 / 1500（**被压在 1400 以下、在 1400 处形成断崖**） |
| 住宅税基算法 | `Σ max(0, Wage − ₡1400) × Labor` | **`Σ Wage × Labor`**（起征点已在字段内） |

**⇒ 换用新导出后必须删掉 `max(0, … − 1400)` 那一层**，否则会把起征点扣两遍、**系统性低估税基**。
代码里由 `WAGE_IS_TAXABLE` 开关控制（`analysis/city_reports.py`），配套函数 `_taxable_from_wage()`。

> ⭐ **口径判定证据（2026-10-13 第八轮实测，两次导出相隔 20 分钟、同一座城）**：
> ① **整段平移**：旧 min = ₡1200 → 新 min = ₡200（**正好 −1000**），
> 旧 p10 = ₡2000 → 新 p10 = ₡1000；旧 max = ₡8157 → 新 max = ₡6501。
> ② **断崖位置**：新分布的**众数桶是 1300–1500，而 1200 以下骤降** ——
> 这正是「减去一个接近 1400 的门槛」的特征（低于门槛的部分被压到 0 附近）。
> ③ **量级自洽**：`Σ(Wage × Labor)` = 50.7 M，与 `Σ(旧 Wage × Labor)` = 84.4 M 的差
> ≈ `36380 劳工 × ₡1400` ≈ 50.9 M 的同一量级。
>
> ⚠️ **`Wage` 不是工资**：新口径下全城人均应税 **₡1394/月** → 反推**人均有效总收入 ≈ ₡2800/月**。
> **引用时必须说"应税部分"，不能说成"工资"**（`references/45` §A1 的五档工资 ₡1500–2700 是**总收入**）。
> ⚠️ **住宅建筑等级对住宅税基几乎没有杠杆**：实测 L1→L5 的人均应税只从 ₡1178 走到 ₡1402 ——
> **住宅侧涨税基的唯一杠杆是学历结构，不是楼高**；而**商/工/办的等级杠杆是实的**（工业 L1→L4 每岗利润 ×1.9、办公 ×1.4）。


> ⚠️ **区级（`Area_Boundary`）的 `Wage` 是另一套口径**（实测约为建筑级的 **30 倍**量级）
> —— **不要拿区级 Wage 去算住宅税基**，住宅税基一律用**建筑级** `Wage × Labor`。
> **交叉验证方法**：分别算 `Σ(建筑Wage × Labor)` 与 `Σ(区Wage × 区Labor)`，
> 两者应当**同量级**（区级往往略低，因为它按区平均、平滑掉了高收入建筑）。
> 差一个数量级就说明口径选错了。

### 1.0.2c ⭐ 坐标参考系（CRS）会变 —— 标定必须自适应

实测多次导出用的投影不同：

| 导出 | `Elevation.tif` bounds | 标定方式与结果 |
|---|---|---|
| 18:44（带城市名前缀） | x[166021,180357] y[-14336,0]（**EPSG:32631 绝对米**） | GeoJSON 归一化值 ×111006 后平移：ox=158767.3, oy=-7204.8 |
| **22:01（无前缀）** | **x[-7168,7168] y[-7168,7168]**（**以地图中心为原点的投影**） | **ox=-7232.1, oy=-7181.5**（= 栅格 bbox 中心 − MapTile bbox 中心） |

**`terrain.solve_utm_offset()` 两种都能自动解出**（判据始终是"建筑 `Elevation` 与栅格高程误差最小"）。
22:01 那次标定质量：**中位误差 0.013 m / P90 0.034 m / 99.5% 建筑在 1 m 内 / 有效率 100%**。

> ⚠️⚠️ **两个已踩过的坑（第八轮修复，务必遵守）**：
> ① **候选范围不能从栅格左上角起算**（`x0 - sx.min()` 这种写法）。
>    本地栅格是"以地图中心为原点"的（`x0=-7168, y0=+7168`），而 GeoJSON 坐标是
>    以 **`Network_Centerline` bbox 左下角**为原点的（`_origin()`），两者差了好几公里 ——
>    用左上角起算会把搜索窗推到离真值 4 km 的地方，**粗搜步长下只剩伪极小值**
>    （实测错误解 ox=-3200 的中位误差只有 0.069 m，看起来"很小"，但 P90 高达 28 m、只有 74% 建筑在 1 m 内）。
>    **正确做法：用 MapTile bbox 中心对齐栅格 bbox 中心当锚点**（两者覆盖同一块地图）。
> ② **判优不能只看中位数**：本图是**台地地形**（约 48% 面积坡度 <0.5°，大量像素等高），
>    错误平移也会让大部分建筑落在某个台地上、中位误差很小。
>    **必须同时看 P90 与"1 m 内占比"**。
> ③ **不要把高程转成整数**（`astype(np.int64)`）：会把 0.1 m 的量化精度放大成 1 m 的系统误差。

### 1.0.2d 道路流量 `Volume`（拥堵诊断的基础）

* `Network_Centerline.Volume` = 路段**车流量**；`Lane` = 车道数。
* **`Lane == 0` 的路段必须先排除**（铁路 / 地铁 / 步道 / 部分水道，实测约占全部线要素的 **19%**），
  否则 `Volume ÷ Lane` 会把"没有车道"算成"极拥堵"。工具：`CartoData.roads_with_flow()`。
* **单车流量 `Volume ÷ Lane`** 是与路段长短无关的负荷量，用于横向比较。
* **官方从未公布道路通行能力（pcu/h）**（C8，4 次确认）→ 只用**同城同等级路段的相对分位**判拥堵。
* 各等级的里程/车公里/负荷占比**每次从报告 §3、§19 读取**，不要沿用任何历史数值。

### 1.0.2e ⭐⭐ 里程/面积必须**裁剪到已解锁地块**（重要口径）

**问题**：`Network_Centerline` 的几何会**伸出已解锁地块之外**（城际高速、铁路尤其严重）。
按整张地图统计里程会**系统性高估城内设施**，进而误导规划建议。

**解法**（`carto_reader.py`）：
* `CartoData.unlocked_tiles()` —— 已解锁地块（`Object == 'MapTile'` 且 `Unlocked` 为真）。
* `CartoData.apply_unlocked_clip()` —— 把「已解锁范围内的长度/面积」**注入各要素**，
  之后所有 `f.line_length()` / `z.polygon_area()` **自动使用裁剪口径**
  （原始值见 `full_line_length()` / `full_polygon_area()`）。
  > 这样做的理由：分析函数里到处都在调 `line_length()`；逐个改容易漏，以后新增分析又会忘。
* `clip_length_to_features()` / `clip_polygon_area_to_features()` —— **精确裁剪**
  （求交 → 按参数 t 分段 → 取子段中点判定 → 累加），**不是按比例估算**。
  配 `RegionIndex`（区域包围盒粗网格）只与相交地块求交。
* ⚡ 性能：分区图斑是 8 m 小格（可上万个），逐个做边求交很慢 → `_polygon_area_fast()` 提供
  「bbox 被某地块完全包住 → 整体在内」的快速通道（绝大多数图斑走这条通道）。

**要看的量与定性结论**（具体数字每次从报告 §3 读）：

| 类别 | 预期情况 |
|---|---|
| **高速 / 铁路 / 水道** | 常有大比例落在**未解锁区**（地图自带）→ 裁剪前后差异显著 |
| **城市道路（Medium/Small/Large）/ 地铁** | 基本 100% 在已解锁区内 → 裁剪前后几乎不变 |

**⇒ 给城内规划建议时只能用「解锁内」那部分**（报告 §3 同时给两个口径）。
**判断方法**：同一类别"全长"与"解锁内"差距大 → 它主要是**地图自带设施**，不能用来论证城内供需。

> ⭐⭐ **非解锁区路网 = 地图自带资源（`SKILL.md` 「路网口径」条）**
>
> 落在**未解锁地块**上的路网（含高速）是**地图作者预置**的：玩家没修、不拥有、
> 也无权在其上规划。因此：
> * **不得作为「路网等级失衡」的证据** ——
>   用「全图高速 X km / 高速占全路网 Y%」论证"高速过剩""高速穿城"是**误判**；
> * **任何等级结构比较都必须先剔除这部分**，只用「解锁内」口径；
>   代码里 `line_length()` 已裁剪、`full_line_length()` 是全长，
>   两者之差即 `*_map_native`（报告 §3 会把这个差值写出来，让"剔除了多少"可见）；
> * §19 的拥堵/车道缺陷统计也已整体剔除这类路段（字段 `excluded_map_native`）——
>   **地图自带的路堵不堵、有几条车道，不是本城的问题。**

> **连带影响（重要）**：裁剪会改变 §19 的**负荷分布排序**。
> 未裁剪时高速常因把非解锁区段算进来而虚高居首；裁剪后**城内主要负荷可能落在主干道上**。
> **⇒ 讨论"该不该加宽高速"之前，必须先确认这里的口径是裁剪后的。**

### 1.0.2f ⭐⭐ 组团：**按人口/岗位密集程度划分**，行政区划只用于命名

**要求**：报告正文不应反复出现绝对数字坐标，且**"组团"必须按密度划分**（不是按行政区划）。
`analysis/city_reports.py` 的 `identify_clusters()` + `ClusterMap` 负责这件事。

#### 为什么不能按行政区划划组团

行政边界是**人为划定**的，与人实际聚在哪并不一致 —— 同一个行政区可以既是全城最密的
居住区、又只贡献很少岗位。按行政区划划组团会把"密度实际形成的团块"切碎或错并，
导致"组团间关系"的结论失真。

#### 划分算法（`identify_clusters()`）

| 步骤 | 做法 | 默认取值 |
|---|---|---|
| ① 密度面 | 把建筑的人+岗聚到网格 | **150 m** 网格（≈街区量级） |
| ② 密集核 | 取"有建筑格子"的密度分位作阈值 | **p60** |
| ③ 连接 | 形态学**闭运算**（膨胀 r 格再腐蚀）把相邻密块连成一片 | r = **2** |
| ④ 成团 | 8 邻域**连通域**标记，一个连通域 = 一个组团 | — |
| ⑤ 收尾 | 规模 < 阈值的碎块并入**最近**的组团 | **1500** 人+岗 |

参数在 `city_reports.py` 顶部（`CLUSTER_CELL` / `CLUSTER_DENSITY_Q` / `CLUSTER_MIN_MASS`
/ `CLUSTER_CLOSE_R`），**可按城市规模调整**：

* **格子取街区量级**（150 m 左右）：再细会把一个片区打碎成几十个小块，再粗会把相邻片区并掉；
* **分位越高留下的组团越少越聚焦**，越低越碎。判据是"最密的 N% 格子承载了多少人+岗" ——
  先看这个集中度，再决定分位；
* **组团数量没有标准答案**。合理的结果应满足：各组团的**职住比有区分度**（否则说明没分开），
  且组团数在 **4–10 个**量级便于叙述。数量明显偏离就调分位/最小规模。

#### 命名：行政区划**只做锚点**

`<主导行政区>·<相对城市中心方位>组团`。

* 行政区给出"这是哪一片"；
* **方位基准是城市人口重心**（不是行政区中心）—— 这样"中心组团"确实在中心、
  "东北组团"确实在东北，与读者空间直觉一致；
* 离重心最近的组团命名为「中心组团」。

#### 三个易错点（都实测踩过）

1. **`between()` 必须"就近归属"**：公交/道路线路常跑在组团**之间的空隙**里，
   若只认"点在密核内"，绝大多数线路判不出归属。
   加 `snap_km`（默认 0.8 km）：核外则归给该距离内最近的组团。
2. **环线/往返线不能拿字符串当键**：`between()` 会给出「A ↔ B ↔ A」，
   与「A ↔ B」不相等 → 明明连通的组团对被判成**无线路**
   （实测曾把 10 对连通误判成只剩 1 对）。所以要用 `route_cluster_pairs()`
   解析成**无序对集合**。
3. **职能分类看职住比**：`>1.5` 就业主导、`<0.5` 居住主导、其间职住混合。
   **若一个「就业主导」组团都没有**，本身就是重要发现（岗位分散、缺就业中心 →
   公交难以用一条干线覆盖"多点到一点"，只能做网格化接驳），要写进结论。

#### 这套语言的价值

用「**哪个组团 ↔ 哪个组团**」表述，比罗列坐标更能直接指导线路规划：
* **有直达线路的组团对** 与 **无直达且在合理补线距离内的组团对** 一眼分开；
* 把"人口最集中的组团"与"岗位密度最高的组团"配成对 → **通勤主轴**，
  也是公交最该强化的一对；
* 具体数值**一律从该次报告 §1.1 读取**，不要沿用任何历史范例里的数字。

### 1.0.2g ⭐ 配图：精度要求与"建议必配图"

**要求**（用户明确提出）：① 辅助图里**干道绘制不能有偏差**，不必画全部路网，
但画出来的路网/铁路/交通网**必须正确**；② **给公共交通建议时要同时给出配图**。

#### 干道正确性已验证

* 几何取自 `Network_Centerline`（**中心线**），不是 `Network_Boundary` 的**路幅多边形**
  —— 后者画出来会偏宽、且交叉口处会糊在一起。
* **核验方法**：几何长度 ÷ 属性 `Length`（游戏内真实米数）。
  实测各类别比值**中位 1.001–1.005**、p10–p90 约 0.96–1.08 → **位置与比例是准的**。
  做图之后如果怀疑"干道画偏了"，先跑这个比值自检，不要凭观感判断。
* **裁剪**：默认只画已解锁地块内的部分（`clipped_parts()`），否则会"画出城市之外的路"。
* **层级**：高速=暗红最粗、大路中灰、主干冷灰、支路极浅（只作底纹）、
  铁路/地铁近黑；干道**后画**以压在底层之上。图例**只列真正画出的等级**。

#### 两种地图模式

| 用途 | 图层 | 说明 |
|---|---|---|
| 全路网 | `roads` | 画到支路，用于看整体肌理 |
| **干道（推荐用于建议配图）** | `roads,arterial` | **只画高速/大路/主干 + 铁路地铁**，不画支路 |
| **组团公交可达性** | `clusters,roads,arterial,transit` | 组团按"有轨道/仅公交/**无直达**"着色 |

#### 组团图的三色语义（给公交建议时最关键的一张图）

* 🟩 绿 = 该组团**有轨道**服务
* 🟦 蓝 = **仅地面公交**
* 🟥 **红 = 没有任何线路直达 → 优先补线的对象**

> ⚠️ **实现坑**：组团标签必须**分两遍画**（`fills` / `labels`）。
> 若和色块一起画，后面的线路与站点文字会压掉组团名，整张图就读不了。
> 标签要加**白底文字框**，否则压在彩色线网上同样看不清。

#### 干道正确性：**已用四种独立方法核验，几何本身没有偏差**

怀疑"图上干道画偏了"时，**先跑这四项自检，不要凭观感改代码**（本项目已实测）：

| 核验 | 方法 | 实测结果 | 结论 |
|---|---|---|---|
| ① 长度一致 | 几何长度 ÷ 属性 `Length`（游戏内真实米数） | 各类别比值**中位 1.001–1.005** | 位置与比例准 |
| ② 像素往返 | `Mapper.px()` → `px_to_geo()` 回推 | 最大误差 **0.000000 m** | 投影无误差 |
| ③ 各向同性 | 1000 m 映射到像素的水平/垂直/对角长度 | 水平=垂直=**207.78 px**，对角/水平=**1.414214=√2** | **无拉伸、无剪切** |
| ④ 线路贴合路网 | 线路顶点到最近道路线段的距离 | 地铁/火车中位 **2.0 m**、公交 **3.0–5.5 m**（≈路幅半宽） | 线路确实沿路走 |

> **④ 的一个例外要认清**：`货船路线` 到道路的距离中位 **50 m**、到 `Waterway` 中心线的距离是
> **恒定 50.0 m（p90 50.1 m）** —— 这是**航道车道偏移**，不是错误。
> 别把它当 bug"修掉"，也不要用"是否在陆地上"来判断（水面色带只有 ~50 m 宽，
> 采样点落在色带外会被误判成陆地）。

**⇒ 结论：`Network_Centerline` 的几何是正确的。** 图上"看起来偏"通常来自三件事，按此顺序排查：
1. **画了全部支路** → 干道被淹没、主次不分（**默认已改为只画干道级**）；
2. **没有裁剪到已解锁地块** → 图上出现"城市之外的路"；
3. **图例与画面不一致**（只画干道却还列着支路）→ 读者以为漏画。

> ⚠️⚠️ **第 4 条（本项目第十轮踩到，最严重）：把同名路段首尾相接，或用合并 bbox 当"这条路"。**
> 一条"路"在数据里是**几十条独立路段要素**，**文件顺序与地理位置无关**。
> * 首尾相接画一条线 → **用直线把互不相邻的路段连起来**，图上出现不存在的路段
>   （实测 `繁荣路` 47 段被画成一条横贯 5 km 的斜带，那几道平行长线就是这个 artifact）；
> * 用合并 bbox 当端点 → 端点是**别处的同名小段**的角点，**一个坐标就把建议说错片区**
>   （实测把"繁荣路南端"写成 y=8105，那其实是 900 m 外一条 0.18 km 小段的端点）。
>
> **正确做法**：`core/roads.py` 的**连通段（run）+ 沿线里程 s** 口径 ——
> `繁荣路` = **主连通段 4.86 km（s 0→4861，(4550,8931)→(8208,12088)）**
> ＋ **0.18 km 独立小段（(7095,8213)→(7244,8105)）**。
> 报告里写"xx路沿线"时用 `路名 主连通段 沿线 s₁–s₂ m` + 两端锚点。
> **完整口径与用法见 `references/80` §3.0 与 `SKILL.md` 「沿线定位」条。**

#### 图层与默认值

| 模式 | 图层 | 用途 |

| **默认** | `roads,arterial` | **只画高速/大路/主干 + 铁路地铁，不画支路**。辅助图不必画全部路网 |

### 1.0.3 ⭐⭐ 坐标标定：GeoJSON ↔ GeoTIFF（**极易踩坑**）

**问题**：GeoTIFF 是 EPSG:32631 **绝对米**，新版 GeoJSON 是**归一化值**（×`GEOJSON_SCALE`=111006.1 才变成米）。
两者**必须先解出一个平移量**才能把地形与建筑对上。**不做这一步会得出"栅格不覆盖城市"的错误结论**
（本项目第七轮报告就因此把地形结论整段剔除了）。

**解法**（`core/terrain.solve_utm_offset()`，纯数据自洽、不依赖任何文档）：
建筑自带 `Elevation`，栅格 `Elevation.tif` 是同一套地形 → 搜索使两者**中位误差最小**的平移量。

**标定质量的判据**（每次都要看，不要假设固定值）：中位误差应 ≈ 数据本身 0.1 m 的量化精度
（即**远小于 1 m**）；平均误差与 P90 也要小。`solve_utm_offset()` 会返回质量字典，
误差偏大说明标定没解对，**不要继续用地形结论**。

**独立验证**（不是循环论证）：标定后建筑处的**坡度中位应接近 0°**（城市建在平地上），
而同图地形的整体坡度中位明显更大 —— 两者对比即可自证。
若建筑处坡度也很大，说明标定错了，或这座城市确实建在坡地上（用 `references/70` §1.0.4 的分级确认）。

> 地图地形常见形态：**台地式**设计（大片面积坡度很小，其后直接跳到较大坡度），
> 台地高程集中在少数几个值上，**水体为高程 0 的平坦区**。
> 这些是地图生成器的特征，**不是缺陷**，按 §1.0.4 分级处理即可。

> ⚠️ **GeoTIFF 地理参考的两个坑（已修）**：
> ① `ModelTiepoint` 的定义是"**像素 (i,j) 的中心**对应地理 (X,Y)"，所以左上角是
>    `x0 = X - i·sx`、`y0 = Y + j·sy`。早期实现直接把 tiepoint 的 X/Y 当左上角且 y 用减号，
>    导致**所有栅格整体偏移**（本地栅格偏 21504 m、世界栅格偏 86016 m），高程永远对不上。
> ② 坐标→像素必须用 **`floor`**；`int()` 对负值向零截断，会错位一个像素。

### 1.0.4 可建造性分级（`core/terrain.py`）

`buildability()` 输出 `水体 / 陡坡 / 缓坡 / 适宜 / 地图外` 五类，判据见 `references/80`。
`classify_point(grid, utm_x, utm_y)` 查点、`is_buildable()` 判布尔值。
⚠️ **`classify_point` / `verdict_text` 收的是"已平移"的坐标** —— 调用方必须自己加平移量
（`city_report.py` 的 `BUILDABLE()` 内部完成这一步），否则会得到一片 `无数据`。

**自检方法（每次必做）**：现有建筑应当**绝大多数落在「适宜」**（若出现大量建筑落在陡坡/水体，
说明标定或分级错了，先查 §1.0.3）。同时报告会给出"地图内"与"已解锁区内"两套占比 ——
**规划只用后者**，因为前者含大片不可达区域。
建筑高程的集中带、城市高差等**每次从报告 §8.3 读**。

```
│  └─ WorldDepth.tif       4096×4096, 14.0 m/px
└─ Styles/                  QGIS 样式（.qml），可直接拖进 QGIS 出图
```

## 2. 关键前提

- **几何类型是 Z 型**（PolyLineZ=13 / PolygonZ=15 / PointZ=11）。布局为
  `[BBox 4d][NumParts][NumPoints][Parts][Points(XY)][Z 数组][M 数组]`，
  只取 XY 时偏移量与 2D 版本一致。很多简易 shapefile 解析器只认 3/5/1，会读出 0 条 ——
  这是最常见的踩坑点。
- **属性表文本是 GBK**（中文），不是 UTF-8。按 UTF-8 解会得到 `å®¢è¿` 这类乱码。
  正确做法：先试 UTF-8，失败回退 GBK。
- **坐标系 EPSG:32631（UTM 31N）**，单位米，但 x 值集中在 16.5 万附近 ——
  这是 CSL2 地图的局部坐标，不是真实地理坐标。城内距离直接用欧氏距离即可。
- 线路数据里的 `Length` 是**线路总长（含往返）**，单位米；`Passenger` 是**当前在线乘客数**，
  `Vehicle` 是**车辆数**，`Usage` 是**车辆使用率（小时/辆·某种归一）**。

## 3. 字段表

### 3.1 Network_Centerline / Network_Boundary（994 条典型）

| 字段 | 类型 | 含义 | 典型取值 |
|---|---|---|---|
| Name | C(30) | 道路名 | 沙棘街、克莱斯特伍德公路 |
| Asset | C(39) | 道路资产名 | 单向双车道高速公路、四车道道路、双线铁路、普通航道、人行道 |
| Category | C(26) | 道路等级 | Highway / Medium / Small / Train / Waterway / Pathway；可带 `, Bus` / `, Bicycle` 后缀表示有公交/自行车道 |
| Direction | C(14) | 通行方向 | Forward（单向）/ Both（双向） |
| Elevation | F(13,4) | 高程 m | 281.63 |
| Form | C(14) | 形态 | Normal / Elevated（高架）/ Tunnel（隧道） |
| Lane | N(1) | 车道数 | 0（铁路/航道）、1、2、3、4、5、6 |
| Limit | F(3) | 限速 km/h | 20 / 40 / 50 / 80 / 100 / 120 / 160 |
| Object | C(14) | 对象类型 | Road / TrainTrack / Waterway / Pathway |

> **方向拆分**：CSL2 的双向道路在数据里可能是 1 条 `Both` 记录，
> 也可能是 2 条方向相反的 `Forward` 记录（高速公路几乎总是后者）。
> 因此"高速公路里程"按中心线累加会把双向车道**算两遍**，报数时要说明口径。

### 3.2 Zoning_Boundary（9093 条典型）

| 字段 | 含义 | 取值 |
|---|---|---|
| Name | 建筑/地块类型名 | 中式低密度四合院、欧洲中密度住宅、工业设施… |
| Color | 十六进制色 | #32EC32 |
| Object | 对象类型 | Zoning |
| Zoning | **分区主类** | Residential / Commercial / Industrial / Office / Residential, Commercial（商住混合） |

> ⚠️ **图斑不是地块，面积不可当"用地面积"用。** 实测每个图斑是 **8 m × 8 m ≈ 64 m² 的固定栅格单元**
> （实测 9,093 个图斑的面积几乎完全相同，标准差/均值 < 2%）。所以：
> - **图斑数**（每个分区有多少个单元）是可靠的相对指标；
> - **图斑面积合计 ≈ 建成占地栅格总量**，会系统性低估真实用地面积，**不要写成"住宅用地 0.36 km²"**；
> - 密度层级只能看 `Name`（低/中/高密度、排屋、四合院…），不能从面积推。
>
> ⚠️⚠️ **图斑里混有大量非建筑对象。** 实测分区图斑数往往是**建筑栋数的十倍以上**
> （一座两万余图斑的城市只有千余栋建筑），**分区图斑面积合计明显大于建筑实际占地**。
> 说明图斑还包含路面、地块轮廓、围栏、道具等。**因此绝不能靠"某图斑离建筑很远"去列"闲置地清单"
> （假阳性极高，本项目实测后已废弃这种做法）**，只能在**分区类型之间**做相对比较 ——
> `city_report.py` §12 就是这么做的：比较各用途的 `建筑占地 ÷ 已划区面积`。
>
> `city_report.py` 会**自动检测**这种"面积高度一致"的情况并在报告里打警告，同时给出建筑层面的
> 密度层级分布（按建筑名统计）。

### 3.3 Building_Boundary（672 条典型）

| 字段 | 含义 |
|---|---|
| Name | 建筑类型名 |
| Addr_dist / Addr_strt / Addr_nmbr | 所在区 / 街道 / 门牌号 |
| Asset | 资产名 |
| Category | 类别 |
| Employee | **该建筑提供的岗位数** |
| Resident | **该建筑的居民数** |

### 3.4 Route_Centerline（条数 = 线路数）

| 字段 | 含义 |
|---|---|
| Name | 线路名（客运火车路线 1、公交路线 1…） |
| Color | 线路色 |
| Length | **线路总长 m（含往返）** |
| Passenger | **当前乘客数** |
| Stop | **车站数** |
| Transport | Bus / Tram / Subway / Train / Ferry / Ship / Airplane |
| Usage | 车辆使用率。**单位未公开** —— 实测某线路为 17.083（同期 Vehicle=9、Passenger=123），**不能当百分比读**，只能在线路之间横向比。判断"是否该加车"要看游戏内 Line 面板的**使用率百分比** |
| Vehicle | **投入车辆数** |
| Weight | 权重（多为 0） |
| Object | RoutePassenger / RouteCargo |

> **线路几何既可能是"往返"也可能是"闭合环线"**：实测部分线路首尾顶点几乎重合（距离 < 50 m）。
> 判断方法：首尾点距离 ≈ 0 → 环线，几何全程即一圈；否则按往返处理，只铺前半段。
> `city_report.py` 的 `_station_span()` 就是这么做的，并在报告里标注站距口径（"环线一圈"/"单程"/"不可算"）。
> **站数 ≤ 2 时站距不可算**（会输出「—」），不要拿端点直线距离当站距。

> ⚠️⚠️ **口径分界（`Object` 字段的唯一用途）：客运指标一律只取 `RoutePassenger`。**
> `Object = RouteCargo` 的是**货运铁路 / 货运航线**（实测某城 `RouteCargo + Ship` 2 条，`Passenger = 0`）：
> * **不进** `Passenger / Vehicle` 派生的任何客运指标（人·车、人·km、乘客合计、按方式汇总、线网规模）；
> * **不进**走廊重叠判定，也**不进** `--trend` 的"逐线乘客趋势"；
> * 它们的**车辆数 / 线路数 / 长度**只在**工业部分**做辅助分析
>   （`city_report.py` 的 `transit["cargo_routes"]`；判据见 `SKILL.md` §2「货运与产业链」）。
> * 实现：`analysis/city_reports.py` 的 `is_passenger_route()` / `cargo_routes()`
>   —— **唯一分界实现，不要在别处手写 `Object` 判断**。
> * ⚠️ 老版导出**没有** `Object` 字段 → 缺字段时按**客运**处理，避免误删客运线。

> 🛑 **`Vehicle == 0` 的线路 = 停用线路。**
> * **不做任何客流分析** —— 不参与「人/车」、人·km、估算间隔、效率排序、**客流合计与中位数**；
> * **只做线位分析**：走向、长度、站数、覆盖贡献、是否与既有走廊重复；
> * 报告必须**单独列出停用线路清单**，并给两条处方：
>   ① **恢复配车**（线位仍有用）② **撤线**（线位已被其它线路覆盖）；
> * ⚠️ **不得**把它们混进"低效线路"里去批评 —— 乘客数低是"没车"造成的，不是需求不足的证据。
> * 同一口径见 `30-public-transport.md` A3.8、`46-algorithm-roadmap.md` T6。

> ⭐ **线路里程口径（唯一口径）：线路总里程 = 逐线路 `Length` 相加。**
> **单线明细表、按方式汇总、线网规模、线网密度全部用这一个口径。**
> 线路里存在**掉头 / 绕行 / 环线**等因素时，**线网统计口径的合计会与逐线明细对不上** ——
> **两处数字不一致时，以「逐线路长度相加」为准**，并且**不再保留另一套合计去"核销差额"**
> （不给两套数、不写"差额说明"）。
> 逐线路长度本身仍是 `Length`（**含往返**，见上表），环线 / 往返的判定见下。

>   这里把它写成显式排除，是为了让口径可审计、并防住将来出现 `StopSubwayYard` 这类新类别。

## 4. 常用派生指标与算法

> ⚠️ **范围限制（本表专用）**：下表带 `Passenger` / `Stop` / `Vehicle` 的**线路类指标**
> 只对 **`Object = RoutePassenger`** 的线路成立 ——
> **货运铁路 / 货运航线（`RouteCargo`）不参与**（`Passenger` 恒为 0，会把中位数与合计拉偏）；
> **车站腹地 / 站点覆盖**只对**客运站点白名单**成立（见 §3.6），**depot（含地铁总站）与货运站点都不算**。
> 货运类的派生量只在**工业部分**做辅助分析（`SKILL.md` §2）。
>
> 🛑 **另加两条范围限制（同样适用于本表全部线路类指标）**：
> ① **`Vehicle = 0` 的停用线路不参与任何客流指标**（人/车、人·km、估算间隔、效率排序、
> 客流合计与中位数），**只做线位分析**，并在报告里**单独列清单**（见 3.4）；
> ② **线路总里程一律 = 逐线路长度相加**，与单线明细、按方式汇总、线网规模、线网密度**同一个口径**（见 3.4）。

| 指标 | 算法 | 注意 |
|---|---|---|
| 人口 / 岗位 | Σ Building.Resident / Σ Building.Employee | **与 District 汇总不是同一口径**，两者会有小差异（实测 2,810 vs 2,804），报告里两个都给 |
| 职住比 | 岗位 / 人口 | **官方从未给出"健康区间"数值**；只能看结构性问题（岗位远少于人口 → 被迫长距离通勤） |
| 分区占比 | Σ 图斑面积（按 Zoning） / 总面积 | ⚠️ 图斑是 8 m 栅格单元，**面积不是用地面积**；**图斑数更可靠**（见 §3.2） |
| 线路人/车 | Passenger / Vehicle | **只做同方式内部比较**。**必须与容量归一的「线路效率」同时给** —— **只按「人/车」横向排序会把"地铁车大"误读成"地铁低效"**；低于同方式中位数即低效线（`[经验]` 判据）。**`Vehicle = 0` 的停用线路不参与**（见 3.4） |
| **线路效率（容量归一）** | `Passenger / (Vehicle × 单车容量)` | 单车容量见 `40-number-tables.md` 1.3（公交 **80** / 地铁 **1080** / 客运火车 **840** 人/辆）；**电车 / 单轨 / 渡轮 / 缆车容量未知 → 不做归一、留空**。**跨方式排序列用本行；使用率判据仍以游戏内 Line 面板的百分比为准** |
| 线路人/km | Passenger / (Length/1000) | 剔除"长而空"的线；**停用线路不参与** |
| 平均站距 | 环线：`Length/(Stop−1)`；非环线：`Length/2/(Stop−1)` | 站数 ≤2 时不可算。**Length 含往返**，别忘除 2 |
| 估算间隔 | `2 × (Length/2 / v) × 60 / Vehicle`，v 取 20–25 km/h | 只用于**线路之间横向比较**。**`Vehicle = 0` 时不可算**（停用线路，见 3.4）。完整式还含 `站数 × 单站停站时间`（官方未公布），见 `30-public-transport.md` B4.1 |
| 车站腹地 | 以站点为圆心 r 内 Building 的 Resident/Employee 求和 | 常用 r = 400 / 600 / 800 m。**Carto 不导出站点几何**，站点位置靠"沿线路等分 `Stop` 个点"近似 |
| 走廊重叠 | 两条线重采样后逐点最近距离 | **400 m 内占比 ≥ 80% 视为同一走廊**（50–80% 部分重合） |
| 就业中心 | 400 m 网格聚合 Employee 后取 Top-N | 与线路站点腹地交叉验证 |
| **路网通勤距离** | 由 `Network_Centerline` 建图（节点按 25 m 吸附，边权 = 长度 ÷ 限速），跑 Dijkstra | **必须用路网距离，不能用欧氏距离**（会低估绕行）。见 `scripts/core/network_graph.py` 与 `city_report.py` §18 |
| 高速里程口径 | 按 `Category` 累加 | ⚠️ 高速在数据里**按方向各记一条**（`Direction=Forward`）→ 里程含双向路幅，约为实际道路长度的 2 倍 |

## 5. 已知局限

> ⚠️ **本节的"没有"清单已经过期过两次**，请以下面的**现况**为准（2026-10-13 第八轮复核）：
>
> | 曾经的"没有" | **现况** |
> |---|---|
> | 没有建筑等级 | ✅ **新版 GeoJSON 有 `Level`**（L0–L5），报告 §8.2 直接用 |
> | 没有公司利润 | ✅ **有 `Profit`**（₡，按栋），报告 §8.2 直接用。<br>⚠️⚠️ **但它永远不会写成负数** —— 付不起 `upkeep` 的公司**先降级、再废弃**，不记负利润，**所以判亏不得用 `Profit < 0`**（实测 212 栋商业 0 栋为负）。<br>**当前判亏口径有两个**：① **`Profit <= 0`（含等于 0；Carto 现成字段，本游戏里实际等于 `== 0`）**；② **月收入 ≤ 月成本**（需游戏内公司面板读数，或将来 Carto 新增字段 —— **Carto 现有建筑层没有月收入 / 月成本字段**）。<br>**空置（`Employee = 0`）与"在营但毫无余量"（`Profit <= 0` 且 `Employee > 0`）必须分开报**：后者才是要处理的对象。<br>⚠️ **商业还要带存档时点**：凌晨（0–5 时）存档读出的亏损**不作为证据**（判据与热门时段见 `45-economy-and-happiness.md` A1.4–A1.5）。**用错口径会让结论完全反过来** |
> | 没有工资 | ✅ **有 `Wage`**（⚠️ 是**应税部分**、不是工资，见 §1.0.2b） |
> | 没有拥堵/车速 | ⚠️ **有路段 `Volume`**（车流量）→ 可算单车流量分位（§19）；**仍然没有车速与通行时间** |
> | 没有服务覆盖率数值 | ⚠️ **有 POI 真实站点坐标 + 官方 `Service range`** → 可算双口径覆盖（§16）；**仍然没有"游戏算出来的有效覆盖"** |
